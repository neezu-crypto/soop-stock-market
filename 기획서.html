1서비스 개요

SOOP STOCK 거래소는 SOOP(숲) 스트리머를 하나의 "종목"으로 삼아, 유저가 가상 자산으로 매수·매도하며 시세 변동을 즐기는 웹 기반 모의투자 서비스입니다. 실제 화폐가 오가지 않는 엔터테인먼트 목적의 팬 참여형 미니게임이며, Firebase Realtime Database를 백엔드로 사용해 모든 유저에게 실시간으로 시세·랭킹이 동기화됩니다.

  • 플랫폼: 단일 페이지 웹앱 (Vanilla JS + Firebase, 정적 호스팅 / GitHub Pages)
  • 대상: 스트리머 팬덤 커뮤니티, 익명 방문자 포함 누구나 즉시 참여 가능
  • 수익 모델: 배너 홍보(우측 랭킹 배너, 차트 하단 광고 배너), 최상단 고정 노출, 중계방 홍보 판매 + 보물상자 판매(후원창 구매 기반 자산 충전) + 플레이타임 초과분 게임머니 충전

4주요 기능

4.1 종목 리스트 & 검색

  • 페이지 진입 시 전체 종목을 1회 조회(get)해 검색/정렬 기준 데이터(allStocks)를 구성
  • 가격순 정렬 후 상위 100개 또는 검색어와 일치하는 종목만 카드로 렌더링
  • 검색창 입력 시 종목명 기준 즉시 필터링 → 노출 목록이 바뀌면 구독 대상도 함께 갱신
  • 등락률에 따라 상승(빨강)하락(파랑) 색상 구분, 카드 내 스파크라인으로 최근 추세 시각화 — 가격 히스토리·등락률은 서버에 저장하지 않고, 클라이언트가 실시간 구독으로 받는 가격 틱을 로컬에 최대 20개까지 쌓아 직접 계산(데이터 사용량 절감)

4.1.1 실시간 구독 최적화 (노출 종목만 갱신)

  • 전체 종목을 항상 실시간 구독하던 방식에서, 현재 화면에 렌더링된 종목만 개별 구독하는 방식으로 전환
  • 검색/정렬 결과가 바뀌어 화면에서 사라진 종목은 구독을 즉시 해제하고, 새로 노출된 종목만 구독을 추가 (syncStockSubscriptions())
  • 보유 중인 종목은 목록에 노출되지 않아도 내 보유 주식 패널의 실시간 손익 반영을 위해 예외적으로 항상 구독 유지
  • 목적: 종목 수가 많아져도 불필요한 실시간 트래픽/DB 읽기 비용이 늘지 않도록 화면에 보이는 데이터만 최신 상태로 유지

4.1.2 스파크라인 서버 저장 구현 완료

4.1의 기존 방식(클라이언트 로컬 최대 20개 누적)은 새로고침하면 히스토리가 초기화된다는 한계가 있었다. "내가 보유 중인 종목만" 새로고침에도 유지되도록 개선했다.

  • 저장(쓰기) — 매매마다, 전체 종목 대상: trade() 체결 마지막 단계에서 최근 체결가 20개(SPARKLINE_MAX, 클라이언트 PRICE_HISTORY_MAX와 동일)를 기존 stocks/{stockId}와는 별도 경로인 sparklines/{stockId}에 롤링 버퍼(트랜잭션)로 기록한다(best-effort — 실패해도 매매 결과에는 영향 없음). 매매 트랜잭션에 얹혀가는 추가 쓰기라 비용은 무시할 수준이고, 롤링 버퍼라 저장 용량도 늘지 않는다. 별도 경로로 둔 이유 — stocks/{id} 안에 필드로 얹으면 그 종목을 구경만 하는(보유하지 않은) 모든 뷰어의 카드 리스너에도 그대로 브로드캐스트돼 "보유자만" 조건이 무의미해진다.
  • 접근 제어: sparklines/{id}는 가격 이력일 뿐 개인정보가 아니므로 candlesticks와 동일하게 전체 공개 읽기(.read: true) · 클라이언트 쓰기는 차단(.write: false)으로 설정 — 별도 콜러블 없이 클라이언트가 필요한 stockId만 골라 직접 get()할 수 있어 구조가 단순하다.
  • 다운로드(읽기) — 세션당 1회, 보유 종목만 대상: onValue(users/{uid}) 콜백에서 myData.stocks 중 보유 수량 > 0인 종목 id만 골라(seedSparklinesForCurrentUser() → seedSparklines()) sparklines/{id}를 get()으로 1회 조회해 priceHistoryBuffer를 채운다. 이미 채운 id는 seededSparklineIds로 기억해 다시 조회하지 않고, 그 이후는 지금처럼 stocks/{id} 실시간 구독으로 들어오는 가격 틱을 이어붙인다(4.1.1의 "보유 종목 항상 구독" 로직 재사용 — 추가 구독 없음). 매매 건수가 아니라 세션 수 × 평균 보유 종목 수에만 비례해, 전체 종목을 항상 브로드캐스트하는 방식보다 다운로드량이 대폭 줄어든다.
  • 관리자 계정 예외 — 전체 종목 대상: 관리자는 직접 플레이(보유)하지 않아 "보유 종목만"으로는 볼 게 없다. 그래서 auth.currentUser?.email === ADMIN_EMAIL이면 보유 종목 대신 allStocks 전체 id를 대상으로 채운다(다른 플레이어 관점에서 전체 시세 흐름을 보기 위함). 관리자는 계정이 하나뿐이라 세션당 다운로드량이 늘어도(전체 종목 수 × 약 200B) 무시할 수준이다. 로그인 시점과 stocks/ 최초 로드 시점의 순서가 보장되지 않아, 두 시점 모두에서 이 시딩을 시도하도록 두 군데(로그인 콜백 + stocks/ 최초 로드 콜백)에서 호출한다 — seededSparklineIds가 중복 조회를 막아줘 두 번 호출돼도 안전(idempotent)하다.
  • 비보유 종목은 기존 방식 그대로(일반 유저): 리스트를 탐색 중인(보유하지 않은) 종목 카드는 서버 저장/조회 대상에서 제외 — 지금처럼 클라이언트 전용으로 계산하고 새로고침 시 초기화되는 동작을 그대로 유지한다.
  • 세션 중 신규 매수 자동 반영: seedSparklinesForCurrentUser()는 users/{uid} 값이 바뀔 때마다(=이 유저가 매매할 때마다) 다시 호출되므로, 세션 도중 새로 산 종목도 myData.stocks에 처음 나타나는 시점에 자동으로 서버 이력을 1회 채워온다(별도 처리 불필요).
  • orphan 정리: 종목 삭제(deleteStocks/cleanupDuplicateStocks)·상장폐지(delistStock) 시 chartBanner·pinnedStocks와 함께 sparklines/{id}도 같이 삭제한다.

4.2 캔들 차트

  • 체결 시마다 candlesticks/{stockId}/{분단위 timestamp}에 OHLCV 데이터 기록
  • 기간 탭(예: 10분/1시간 등)과 분봉 단위 탭을 조합해 조회 범위를 조정
  • 최대 360분 데이터만 보관, 이전 데이터는 주기적으로 삭제되어 DB 용량 관리
  • 차트 호버 시 캔들 정보(시가/고가/저가/종가/거래량) 툴팁 표시

4.3 랭킹 시스템

  • 매매 체결(trade Cloud Function) 마지막 단계에서 서버가 직접 TOP5를 갱신 — 클라이언트가 rankings/top5를 직접 쓰던 방식은 임의 조작이 가능한 구멍이라 서버로 이전됨
  • 거래량 지표는 델타 누적이 아니라 stocks/{id}.volume(누적 거래량) 절대값을 그대로 사용해 드리프트 없이 계산
  • 같은 종목이 너무 잦게 반영되지 않도록 마지막 저장 후 30초 이내면 이번 반영은 건너뜀(디바운스)
  • 집계된 TOP5는 rankings/top5에 저장되어 모든 유저에게 동일하게 노출 (클라이언트는 읽기 전용 구독만 수행)

4.4 홍보 배너 / 광고 — 셀프 신청 & 즉시 적용

과거엔 관리자가 신청마다 "진짜 상장된 스트리머가 맞는지"까지 검수해야 했으나, 현재는 닉네임이 이미 상장된 종목명인지만 신청 시점에 자동 확인하도록 바뀌어 관리자 승인 단계 자체가 사라졌다 — 상장 여부는 상장 신청 승인 시점에 이미 한 번 걸러지기 때문이다. 상장 안 된 이름이면 신청 폼이 "먼저 상장 신청을 해주세요"로 막고, 상장된 이름이면 게임자산 차감과 동시에 즉시 적용된다.

  • 우측 랭킹 배너: 이미 상장된 종목명 검색(자동완성) + 스트리머 아이디 입력 → 아이디 기반 프로필 이미지(stimg.sooplive.com/LOGO/...)를 자동으로 배너 이미지로 사용 → 노출 기간(최대 7일) 선택 → 신청 즉시 적용, 검수 없음
  • 차트 하단 배너 — 유일하게 부분 검수가 남아있는 기능: 슬롯/기간 예약과 배너 이미지 승인이 분리되어 있다. 종목 카드를 클릭해 차트 모달을 연 상태에서 신청하면(그 시점 종목ID가 고정), 신청 즉시 chartBanner/{stockId}에 기간이 예약되지만 배너 이미지(bannerImg)는 비워둔 채 관리자 승인을 받아야 실제로 노출된다 — 사용자가 임의 이미지 URL을 즉시 노출시킬 수 없도록 이미지 검수만은 남겨둔 것
  • 중복 신청 차단: 어떤 종목에 이미지 미승인 상태로 예약된 배너가 있으면(이미지 없이 기간만 예약된 상태), 그 종목에는 다른 유저가 새로 신청할 수 없다 — 차트 모달에도 "⏳ 배너 홍보 승인 검수중이에요"로 표시되고 신청 버튼이 비활성화된다
  • 홍보 페이지 링크 자동 생성: 두 배너 모두 신청자가 입력한 스트리머 아이디로 https://www.sooplive.com/station/{아이디} 링크를 서버가 자동 계산 — 링크를 직접 입력받지 않는다
  • 결제: 신청 시점에 서버(Cloud Function)가 신청자의 보유 게임자산(현금)에서 기간 × 단가를 바로 차감
  • 종목별 개별 노출(차트 배너): 전체 종목 공동 노출이 아닌 chartBanner/{stockId} 단위로 종목마다 독립적인 배너를 설정. 종목이 삭제되면 연결된 chartBanner도 함께 삭제되어 orphan 데이터가 남지 않는다
  • 기간 만료: 노출 기간이 지나면 메인페이지에서 자동으로 숨겨지며, 관리자 페이지의 "만료된 홍보" 탭에서 재연장하거나 완전히 삭제할 수 있음
  • 재신청(우측 배너): 이미 홍보 중(만료 전)인 종목으로 재신청하면, 오늘부터 새로 계산하지 않고 기존 만료일에 이어서 연장됨 — 차트 배너는 종목별 개별 신청이라 이런 특별 처리 없이 그대로 갱신
  • 관리자 페이지의 역할 변화: "신규 신청" 검수 큐는 우측 배너·최상단 고정·중계방에서는 사실상 예전 방식(레거시) 기록 확인용으로만 남아있고, 실제 운영은 "진행중/만료" 탭에서 내용 수정·조기 삭제 위주로 이뤄진다. 차트 배너만 "이미지 승인 대기" 큐가 실질적으로 계속 쓰인다

4.4.1 배너 홍보(종목 카드 프로필 배너) — "종목 소유주 인증" 컨셉의 신규 홍보 상품

우측 배너·차트 배너와 신청 방식(닉네임 검색+아이디 입력 → 즉시 적용, 관리자 검수 없음)은 동일하지만, 노출 위치와 신청 자격이 다른 별도 상품이다. 화면에는 "📢 배너 홍보"로 표시되며(코드 내부 식별자는 cardBanner 유지), 사이드 배너 레일이 아니라 종목 리스트 카드 안(가장 노출 빈도가 높은 화면)에 원형 프로필 사진을 띄우고, "이 종목을 실제로 대량 보유한 유저"만 신청할 수 있게 해 "종목 소유주가 직접 인증하는 홍보"라는 정체성을 준다.

  • 노출 위치(반응형): PC는 종목명 오른쪽에 원형 배지로 나란히 배치, 모바일(2열 그리드로 이름 칸이 좁아짐)은 예전처럼 스파크라인 미니차트 위에 겹쳐 띄운다 — 두 자리 모두 마크업에 렌더링해두고 미디어쿼리로 화면 폭에 따라 하나만 보여준다. 크기는 두 자리 모두 34px 동일
  • 신청 진입점 = 노출 위치 그 자체: 별도의 "신청하기" 배너/버튼을 다른 곳에 두지 않고, 아직 배너가 없는 종목은 같은 자리·크기에 점선 테두리 📢 아이콘(빈 슬롯)이 뜬다. 클릭하면 그 종목명이 미리 채워진 채로 신청 모달이 바로 열린다
  • 신청 자격 — 10주 이상 보유: 서버(submitCardBannerRequest)가 신청 시점에 users/{uid}/stocks/{stockId}.qty를 확인해 CARD_BANNER_MIN_HOLDING_QTY(10주) 미만이면 거절한다. 클라이언트도 종목명 입력 즉시 "현재 보유: N주 — 신청 가능/N주 이상 필요"를 미리 보여주지만, 최종 판정은 항상 서버가 한다
  • 되팔기 방지(자동 삭제): 신청 후 홀더가 매도해 보유 수량이 10주 미만이 되면, trade()의 매도 처리 직후 stocks/{id}의 cardBannerImg/cardBannerLink/cardBannerEndDate/cardBannerHolderUid가 즉시 삭제된다(환불 없음). 신청 모달에 이 규칙을 미리 고지하고, 매도 시점에도 홀더 본인이 10주 미만이 되는 거래면 클라이언트가 한 번 더 확인창을 띄운다
  • 슬롯 독점(선착순 1명): 이미 다른 유저가 그 종목의 배너 홍보를 진행 중이면(만료 전) 신규 신청이 막힌다. 같은 홀더의 재신청은 기존 만료일에 이어서 연장된다
  • 데이터 저장: stocks/{id}에 bannerImg(우측 배너)와 완전히 별도인 cardBannerImg/cardBannerLink/cardBannerEndDate/cardBannerHolderUid 필드를 추가 — 두 상품이 같은 종목에 동시에 붙어도 서로 간섭하지 않는다
  • 관리자 페이지: "📢 배너 광고 통합 관리"의 진행중/만료 탭에 우측·차트 배너와 함께 세 번째 타입("📢 배너 홍보")으로 통합 표시되고, 구매 현황·전체 통계 매출 집계에도 동일하게 반영된다. 별도의 신규 신청 검수 큐는 없다(우측 배너와 동일하게 즉시 적용이라 불필요)

4.5 최상단 고정 노출 — 종목 리스트 최상단 슬롯 판매

종목 리스트는 원래 가격순 정렬이지만, 신청된 종목은 정렬과 무관하게 리스트 최상단에 최대 3개까지 고정 노출된다. 배너와 달리 이미 상장된 종목을 대상으로 하는 기능이라, 신청 폼도 닉네임/아이디 입력이 아니라 종목명 검색(자동완성)으로 대상을 고른다. 관리자 검수 없이 신청 즉시 적용된다.

  • 단가: 시간당 게임자산 1만원 (2026-08-14 인하, 이전 25만원), 최소 1시간 ~ 최대 12시간 신청 가능
  • 슬롯: 동시 최대 3개 종목만 고정 가능 — 신청 시점에 슬롯 여유를 검사해, 가득 찬 경우 신청 자체가 거부됨(관리자가 기존 고정을 조기 해제하거나 만료를 기다려야 함)
  • 재신청(연장): 이미 고정 중인 종목이 재신청되면 우측 배너와 동일하게 남은 시간에 이어서 연장(슬롯을 새로 차지하는 게 아니므로 슬롯 검사 대상에서 제외)
  • 실시간 노출 보장: 고정된 종목이 가격순 top100 밖(원래는 화면에 안 보일 종목)이어도 항상 표시되도록, pinnedStocks/{stockId} 경량 마커 경로를 클라이언트가 상시 구독해 "항상 구독 유지" 대상에 포함시킨다
  • 카드에는 📌 배지와 금색 테두리로 일반 종목과 구분 표시, 검색 중일 때는 안내 카드가 숨겨짐

4.6 중계방 홍보 — 지금 플레이 중인 스트리머 소개

이미 상장된 종목명 검색(자동완성) + 아이디 입력 → 아이디 기반 미리보기 자동 표시 → 신청 즉시 게임자산 차감과 동시에 적용, 관리자 검수 없음. 재신청 시 "연장"하는 배너와 달리 이미 진행 중인 종목은 신청 자체를 거부한다(단순 중복 방지, 연장 로직 없음).

  • 단가: 시간당 게임자산 1만원 (2026-08-14 인하 — 실제 서버 가격은 2026-07-29에 15만원으로 반값 할인됐었으나 이 문서엔 반영이 누락돼 있었음, 원래 30만원), 최소 1시간 ~ 최대 8시간
  • 인원: 동시 최대 3명까지만 등록 가능 — 신청 시점에 인원 초과 여부 검사
  • 노출 위치: 종목 리스트 위 "🎥 중계방" 영역, 클릭 시 방송국으로 새 탭 이동
  • 카드 너비 자동 분배: 등록 인원(1~3명)에 따라 각 카드가 flex: 1 1 0으로 균등 분배돼 100%(1명) / 50%(2명) / 33%(3명) 너비로 자동 조정됨
  • 배너 목록과 동일하게 페이지 로드 시 1회만 조회(실시간 구독 없음)해 비용을 아낀다

4.9 종목 상장 신청 — 없는 종목 무료 신규 상장

검색해도 없는 스트리머를 유저가 직접 상장 요청할 수 있다. 무료지만(비용 차감 없음) 아무 이름이나 즉시 상장되면 도배성 종목이 난립할 수 있으므로, 다른 셀프 신청 기능과 달리 여전히 관리자 승인이 필요하다.

  • 제약: 종목명 최대 12자, 1분에 1회 신청 제한(매크로 방지 쿨다운), 이미 상장됐거나 동일 이름으로 대기 중인 신청이 있으면 거부
  • 승인: 관리자가 승인하면 그 순간 시작가 10,000원으로 새 종목이 상장됨(오타 발견 시 승인하며 이름 수정 가능)
  • 대상: 카카오 연동(또는 관리자) 유저만 신청 가능

4.10 종목 거래 동결 (서킷브레이커)

가격이 무작정 오르기만 하는 걸 막는 안전장치. 매수 체결마다 서버(trade)가 자동 판정하며, 별도 신청 없이 조건 충족 시 즉시 발동한다.

  • 발동 조건: 매수 거래가 실제로 있었던 최근 1분봉 5개의 종가가 전부 100만원 이상이면 그 5번째 매수 체결 순간 동결(평균이 아닌 "전부 다" 조건 — 단발성 펌프에 강함)
  • 동결 중: 매수·매도 모두 전면 차단
  • 해제 제약: 동결 직후 5분간(STOCK_FREEZE_COOLDOWN_MS)은 누구도 해제 불가, 동결을 유발한 계정 본인도 해제 불가 — 그 외 유저가 5분 경과 후 선착순 1명만 해제 가능
  • 해제 방법 2가지: ① 게임자산 100만원 지출 → 즉시 셀프서비스, 200만원 보상(순이익 100만원) + 주가 50만원으로 강제 인하 / ② 라이브 방송 후원(별풍선 50개) → 신청 후 관리자 검수, 100만원 보상
  • 미해제 시: 동결 후 12시간(STOCK_DELIST_DEADLINE_MS) 안에 해제되지 않으면 자동 상장폐지 — 보유 중이던 모든 유저의 주식이 전액 소멸(환급 없음). 상장폐지까지 남은 유예시간은 메인페이지 동결 배너에 카운트다운으로 표시되며, 마감 임박 시 별도 경고가 뜬다
  • 스케줄러: checkFrozenStockDelistings가 주기적으로 실행되어 유예시간이 지난 동결 종목을 자동으로 상장폐지 처리

4.11 내 손익 랭킹 — 순수 매매 손익 순위

보너스·후원 당첨금·홍보 신청 비용 등 매매 외 현금흐름은 전혀 반영하지 않는 순수 매매 손익만 집계하는 익명 리더보드.

  • 계산: 매도 체결마다 trade()가 평단가 기준으로 users/{uid}.realizedPL에 실현손익만 누적하고, 랭킹 확인 시점에 서버가 이 값을 그대로 반영한다 — 미실현(보유 중 종목의 평가손익)은 의도적으로 반영하지 않는다. 현재가는 본인이 소량 매수만으로도 순간적으로 밀어올릴 수 있는 값이라, 대량 보유 물량에 그대로 곱해 마킹하면 팔지 않고도 가짜 이익을 순위표에 영구히 박아둘 수 있는 구멍이 있었다(초기 설계의 결함, 발견 후 수정). 클라이언트가 보낸 숫자는 애초에 신뢰하지 않고 매번 서버가 원본 데이터로 재계산한다
  • "예상 순위 보기"(무료)와 "공식 게시"(유료) 분리: 순위가 궁금해서 캐주얼하게 열어보는 행위 자체에 비용을 매기면 재접속을 유도해야 할 기능이 오히려 재접속을 억제하는 역설이 생긴다. rankings/profitEntries가 인기 TOP5와 동일하게 이미 공개 읽기 경로라, 클라이언트가 이미 들고 있는 내 realizedPL과 조합해 서버 호출 없이 무료로 "지금 게시하면 몇 등일지" 계산해 보여준다(orderByChild('value').startAt(내손익+1)로 나보다 높은 공개 엔트리 수를 세는 방식). 실제로 순위표에 이름을 올려 다른 유저에게 보이게 하는 행위만 유료(checkProfitRanking, 10만원)로 남긴다 — 상시 폴링 억제와 서버 재계산 비용 절감 목적은 그대로 유지됨
  • 대상: 확인/게시 모두 카카오 또는 구글로 계정을 보호한 유저만 가능(어뷰징 방지)
  • 표시: 실제 닉네임 대신 트레이더-XXXXXX 형태의 익명 ID로만 노출, 상위 10명 + 내 순위를 함께 보여줌
  • 저장 구조: rankings/profitEntries/{uid}에 value로 인덱싱(.indexOn)된 경로에 기록해 RTDB 쿼리(orderByChild('value').limitToLast(N))만으로 상위 N명을 조회 — 별도 스케줄 집계 작업이 없다
  • 공유용 카드: 결과 확인 후 "📸 스크린샷 모드"로 세로형(9:16) 카드를 띄운다. 저장/공유 API는 넣지 않고 유저가 직접 스크린샷해서 공유하는 방식 — 표시 항목(익명 ID/상위 3명/날짜/크루 배지) 토글, 테마 프리셋(기본/골드/크루 컬러 — 크루 컬러는 크루명 문자열을 hue로 해시해 항상 같은 크루는 같은 색), 30자 이내 캡션을 조합할 수 있다. PC는 옵션(좌)/카드(우) 나란히, 모바일은 카드가 먼저 보이도록 column-reverse로 순서를 바꾼다

4.14 보유 자산 공유 카드 — "손익 확인한 사람만"에서 "누구나"로 바이럴 범위 확장

손익 랭킹 공유 카드는 100,000원을 내고 랭킹을 확인/게시한 유저만 만들 수 있어 접근 문턱이 있다. 반대로 "내 보유 주식" 패널의 "📸 스크린샷 모드" 버튼은 비용 없이 누구나 자신의 포트폴리오 스냅샷 카드를 만들 수 있어, 팬이 자발적으로 커뮤니티에 공유하는 경로를 넓힌다. 손익 랭킹 카드와 동일한 뼈대(테마 3종·토글형 표시 항목·30자 캡션·PC 좌우/모바일 세로 배치·저장 API 없음)를 그대로 재사용한다.

  • 항상 표시: SOOP STOCK 브랜딩 + 총 자산(현금+보유 종목 평가액)
  • 토글 — 보유 종목 TOP3: 평가액 기준 상위 3종목의 이름과 수익률(%). 하위 토글로 수량·평단가도 함께 켜고 끌 수 있다
  • 토글 — 크루 소속 배지 / 날짜: 손익 랭킹 카드와 동일 로직 재사용(detectMyCrew()가 보유 평가액이 가장 큰 [크루명] 프리픽스 종목을 자동 감지)
  • 총수익률은 의도적으로 넣지 않음: 출석 보상·잭팟·복권·후원 당첨금까지 현금에 섞여 있어, 총자산 증가율을 매매 실력처럼 보여주면 오해를 줄 수 있다. 순수 매매 실력을 자랑하고 싶다면 손익 랭킹 카드(realizedPL 기반)를 이용하도록 역할을 분리했다

4.15 최근 7일 자산 변동 — 하루 1번 스냅샷 + 클라이언트 렌더링

지갑 바의 "내 잔고" 또는 "내 보유 주식" 패널의 총자산을 클릭하면 최근 최대 7일간의 총자산(현금+보유 종목 평가액) 추이를 캔들/스파크라인 중 골라 볼 수 있다. 서버는 숫자만 기록하고, 캔들/스파크라인 렌더링과 집계는 전부 클라이언트(Chart.js)가 계산한다.

  • 스냅샷 기록 시점: 개별 매매마다 기록하면 저장량이 유저 수 × 거래 횟수로 폭증하므로, 하루에 딱 1번(그날 첫 하트비트 또는 첫 매매 시점, common.js의 recordDailyAssetSnapshot())만 users/{uid}/assetHistory/{YYYY-MM-DD}에 {totalAssets, cash, stockValue, at}를 기록한다. user.lastAssetSnapshotDate로 오늘 이미 기록했는지 즉시 판별해, 20초 간격 하트비트마다 무거운 보유주식 가격 조회가 반복되지 않는다
  • 보관 기간: 화면엔 최근 7일만 보여주지만, 자정 근처 타임존 오차 등을 감안해 서버가 ASSET_HISTORY_RETENTION_DAYS(9일)보다 오래된 기록은 매 스냅샷 시점에 함께 정리한다
  • "캔들"의 한계: 하루 1점만 기록되는 구조라 진짜 일중 시가/고가/저가가 아니라, 전일 종가 → 오늘 값을 이은 단순화된 막대다. 모달 안내 문구로 이 한계를 명시한다
  • 신규 유저 경험: 과거 데이터를 소급해서 만들 수 없으므로(애초에 기록이 없었음), 오늘부터 하루씩 쌓이기 시작한다. 데이터가 2점 미만이면 그래프 대신 "데이터가 부족해요" 안내를 보여준다
  • 공유 카드: 손익 랭킹·보유 자산 카드와 동일한 뼈대(테마 3종·토글·30자 캡션)를 재사용하되, 카드 중앙에 작은 스파크라인(Chart.js, 축·툴팁 없이 선만)을 함께 그려 넣는다

4.16 잭팟 종목 — 커뮤니티 합산 매매량 마일스톤

매일(정확히는 당첨될 때까지) 랜덤 종목 1개가 "잭팟 종목"으로 선정된다. 로그인(계정 보호) 유저들이 그 종목을 매매한 수량(매수+매도 합산)이 목표치에 도달하는 순간, 그 임계값을 넘긴 그 매매를 실행한 유저에게 200만원이 즉시 지급되고 다음 잭팟 종목이 자동으로 새로 뽑힌다. 손맛(변동보상형 재미)을 매매 자체에 심지 않고 별도 이벤트로 분리해, 스프레드/수수료/시장충격 기반의 기존 매매 밸런스는 건드리지 않는다.

  • 익명 유저 제외: contributeToJackpot()은 계정 보호(카카오/구글) 여부를 넘겨받아 익명 유저의 매매는 아예 카운트에서 제외한다. 초기 구현에서는 이 제한이 빠져 있어 익명 계정도 진행도에 반영되는 결함이 있었다(라이브 테스트로 발견 후 수정) — 계정당 상한만으로는 "익명 계정을 여러 개 파서 혼자 목표치를 채우고 원하는 계정으로 마지막 트리거만 실행" 하는 셀프 파밍을 막지 못하기 때문에, 다른 현금 보상 기능들과 동일하게 로그인 유저로 대상을 한정해야 한다
  • 혼자 파밍 방지 — 계정당 기여 상한(JACKPOT_PER_ACCOUNT_CAP=100): 한 계정이 아무리 반복 매매해도 목표치 카운트에는 최대 100까지만 반영된다. 목표치가 1,000이면 최소 10개의 서로 다른 로그인 계정이 실제로 참여해야만 도달 가능 — "매매를 확률형 도박으로 만들지 않는다"는 기존 설계 원칙을 지키면서도, 개인 그라인딩이 아니라 진짜 커뮤니티 참여가 필요하게 만든다
  • 목표치 산출(자기 조정형): 목표치 = max(JACKPOT_TARGET_MIN=1000, 전일 최고 매매량 델타 × 20% × 랜덤(±20%)). 트래픽이 적을 땐 하한선 1,000이 사실상 항상 적용되고, 유저가 늘어 실제 거래가 활발해지면 목표치도 자동으로 커진다
  • "전일 최고 매매량 델타" 산출 — 스케줄 작업 없이 저렴하게: 종목별로 그날 처음 거래될 때(jackpot.js의 updateStockDailySnapshot()) stocks/{id}.lastDayVolumeDelta를 스냅샷하고, 그 값을 jackpotDailyMaxDelta(그날 관측된 최댓값)에 실시간 반영한다. 전체 종목을 스캔하는 별도 크론 작업 없이, 실제 거래가 발생하는 종목만 자연스럽게 갱신된다
  • 동시성 처리 — 정확히 한 명만 당첨: 계정별 기여량 갱신과 전역 진행도(jackpot/state.progress) 갱신을 각각 RTDB 트랜잭션으로 처리한다. 목표치를 넘기는 순간의 트랜잭션 콜백 안에서만 wonAt/winnerUid를 채워 넣고, 그 이후 들어오는 모든 호출은 wonAt이 이미 채워진 걸 보고 즉시 반환하므로 동시에 여러 명이 거의 같은 순간 임계값을 넘겨도 정확히 첫 번째 트랜잭션만 당첨자로 확정된다
  • 당첨 처리: 상금 200만원 지급 + "🎰 잭팟 당첨" 도전과제 지급 + jackpotLastWin(종목명·상금액만, 당첨자 개인정보 없음 — 동결 해제 공지와 동일한 원칙)에 공개 기록 + 새 잭팟 사이클 자동 시작
  • 노출: 인기 TOP5 바로 아래 전용 바에 종목명·진행률 바·"진행 N/목표" 숫자를 실시간(jackpot/state 구독)으로 보여주고, 클릭하면 그 종목을 바로 검색한다
  • 관리자 페이지: "🎰 잭팟 종목 관리" 패널에서 현재 진행 상황을 확인하고, 필요 시(최초 부트스트랩, 부적절한 종목 재선정 등) 수동으로 새로 뽑을 수 있다(rerollJackpot 액션)

4.17 복권함 — 즉시 판정 스크래치 복권

계정 보호 유저가 20만원에 복권 1장을 사면, 서버가 그 자리에서 세 자리 숫자(각 자리 1~7, 조합 343가지)를 확정한다. 화면의 "긁기"는 이미 확정된 결과를 보여주는 연출일 뿐이고, 당첨 판정과 지급은 구매 시점에 서버에서 이미 끝나 있다 — 클라이언트가 결과를 조작하거나 재요청할 여지가 없다. 777이 나오면 그 순간 누적 모금액의 90%를 받고 모금액은 100만원(초기값)으로 리셋된다.

  • 익명 계정 파밍 방지: 잭팟·출석 보상과 동일한 이유로 계정 보호(카카오/구글) 유저만 구매 가능 — 익명 계정을 무한정 새로 만들어 무료 초기자산으로 반복 구매하는 것을 막는다. 1인당 구매 개수 제한은 없다(티켓마다 실비용이 들어 많이 사는 건 파밍이 아니라 정상적인 복권 원리)
  • 경제 밸런스: 확률 1/343 기준, 평균적으로 티켓 343장(약 6,860만원)이 팔린 시점에 당첨되고 그때 상금은 누적액의 90%(약 6,264만원 수준)라, 판매액이 지급액보다 살짝 많은 구조(하우스 엣지 약 8~9%)로 설계됐다. 이 게임 곳곳에서 새로 발행되는 현금(출석 보상·잭팟 상금·초기 지급 등)을 회수하는 통화 싱크 역할도 겸한다
  • 모금액 초기값: 0원이 아니라 100만원부터 시작하는 이유는, 게임 초반 첫 당첨자가 너무 적은 상금을 받는 걸 방지하기 위함(모금액이 아직 안 쌓인 상태에서 우연히 초반에 당첨돼도 최소 90만원은 보장)
  • 동시성: lottery/pool 갱신을 RTDB 트랜잭션으로 처리 — 여러 유저가 거의 동시에 구매해도 모금액 누적과 리셋이 순서대로 정확히 반영된다
  • 노출: 인기 TOP5·잭팟 바로 아래 전용 바에 현재 누적 모금액을 항상 보여주고(lottery/pool 공개 읽기 구독), 클릭하면 구매 모달이 열린다. 당첨 시 도전과제 "🎟️ 복권 당첨" 지급 + lotteryLastWin(상금액만, 당첨자 개인정보 없음)에 공개 기록
  • 관리자 페이지: 별도 패널 없이 기존 "전체 통계 요약"에 복권함 현재 모금액과 순이익(판매액-당첨지급액)을 함께 노출하고, "유저 구매 현황"에도 7번째 상품 타입으로 통합된다

4.13 도전과제 — 현금 보상 없는 진행감(마일스톤) 배지

5거래(매매) 로직

11트레이딩 봇 — 실제 유저와 짝지어지는 가상 참여자 (2026-08-27, 사용자 지시 — 구현 완료)

배경. "실제 유저처럼 사고팔고 포트폴리오까지 갖춰진 봇"을 만들어달라는 요청. 요청 중 "봇도 접속자 수를 올린다"는 부분이 실제 사람 수를 나타내는 지표를 봇으로 채우는 것이라, 구현 전 기존 stockSimulator.js(관리자 전용 차트 활성화 도구)가 이미 "봇 거래는 차트만 살아있게 하고 유저 보상·랭킹 등 실제 유저를 대표하는 값은 절대 건드리지 않는다"는 원칙을 갖고 있던 점을 근거로 우려를 전달했다. 사용자가 검토 후 "봇도 접속자 수에 그대로 포함"을 확정해, 요청 원안대로 구현했다.

발동 조건 (둘 다 충족해야 봇 생성)

  • 조건1 — 접속 30초 경과. 클라이언트가 최초 접속 시 presence/stockMarket/{'{uid}'}.connectedAt을 심어두고(주기 갱신은 update()라 이 값을 덮어쓰지 않음), 서버가 이 값 기준으로 판정.
  • 조건2 — 실제 유저가 거래할 때마다 20% 확률. 이미 짝지어진 봇이 있으면 이 조건은 건너뛰고(1인당 1개, 재추첨 없음) 항상 반응한다.

거래 반응 패턴 (5종, 각 20%)

매 반응마다 아래 중 하나를 무작위로 골라 실행 — 1~3번은 사용자 지정, 4~5번은 "기타 다양한 패턴 추천" 요청에 맞춰 추가.

패턴동작
① 모멘텀 추종같은 방향으로 5~10회 연속 매매
② 역추세반대 방향으로 5~10회 연속 매매
③ 추종 후 반전같은 방향 5~10회 → 반대 방향 5~10회
④ 분할 매집 후 일부 차익실현같은 방향으로 5~10회 나눠 담았다가, 반대 방향으로 더 적은 횟수(2~4회)만 정리 — 물타기/불타기 후 일부만 차익실현하는 흔한 리테일 패턴
⑤ 관망 후 뒤늦은 반응잠깐 대기한 뒤 같은 방향으로 소수(2~4회)의 주문만 몰아서 실행 — 느리게 반응하지만 확신은 강한 트레이더

모든 주문은 봇 자신의 자산(botUsers/{'{botUid}'})과 보유 수량 안에서만 체결된다 — 매수는 현재가 기준 감당 가능한 최대 수량, 매도는 실제 보유 수량으로 자동으로 캡핑되고, 부족하면 그 주문만 조용히 건너뛴다(실제 유저의 잔액 부족 처리와 같은 결).

구현 — 기존 인프라 재사용

새 폴링/스케줄러를 만들지 않기 위해(stockSimulator.js의 기존 설계 원칙과 동일) 별도 스케줄러는 두지 않았다. 시세·거래량·캔들·스파크라인 갱신은 stockSimulator.js의 executeSimulatedTrade를 그대로 재사용해 실제 거래와 동일한 흔적을 남기고, 봇 존재 동안의 presence 유지는 기존 heartbeat() 함수에 얹어(실제 유저의 하트비트가 오는 동안만 봇의 lastSeen도 갱신) 별도 로직 없이 기존 "60분 유예 후 자동 감소" 규칙을 그대로 함께 따르게 했다. 잭팟 기여·도전과제 지급은 stockSimulator.js와 같은 이유(보상 대상이 될 실제 사람이 없음)로 봇 거래에서 제외했다.

재설계 — 봇도 "1초에 한 거래" 속도 제한(2026-08-27, 사용자 지시 — "봇의 매매속도도 실제 유저처럼 1초당 1거래만 가능하게 해줘"). 처음엔 봇 반응을 실제 유저의 trade() 호출 안에서 끝까지 await해 실행했는데(Cloud Functions는 응답 후 인스턴스를 곧바로 재활용할 수 있어 순수 fire-and-forget은 위험하다고 판단했었음), 속도 제한을 걸자마자 이 설계가 무너졌다 — 패턴③④처럼 최대 20건짜리 반응은 1건당 1초 이상 간격을 두면 총 20초 가까이 걸리는데, 그동안 실제 유저는 자기 매수/매도 버튼 하나 누른 응답을 20초나 기다려야 했다. 그래서 완전히 분리했다:

  • trade.js는 더 이상 봇을 호출하지 않는다 — 실제 유저 거래는 봇과 무관하게 항상 즉시 응답한다.
  • 새 onCall triggerBotReaction({stockId, type})을 추가해, 클라이언트가 trade() 응답을 받은 직후 기다리지 않고(catch만 걸고 await 없이) 별도로 호출한다 — 이 함수는 완전히 독립된 요청이라 자기 속도(1초에 한 거래)대로 20초를 쓰든 말든 실제 유저 화면에는 영향이 없다.
  • 악용 방지 — 이 함수를 거래 없이 반복 호출해 20% 스폰 확률만 계속 재추첨하는 걸 막기 위해, 서버가 users/{'{uid}'}.lastTradeTime이 최근 10초 이내인지 검증한 뒤에만 동작한다.
  • TRADE_COOLDOWN_MS(1000ms)를 common.js로 공용화해 trade.js·tradingBot.js 양쪽이 같은 값을 쓰게 했고, 봇의 주문 간격(ORDER_DELAY_MS)도 이 값보다 항상 크게 잡았다. 추가로 placeBotOrder 안에 봇 자신의 lastTradeTime 기준 쿨다운 검사를 방어선으로 하나 더 뒀다(타이밍 상수가 나중에 바뀌어도 이 규칙만은 항상 지켜지도록).

중복 거래 방지 — 유저 1명당 봇 반응은 한 번에 하나만(2026-08-27, 사용자 지적 — "봇이 거래 진행중일땐 이후 연속으로 트리거가 작동해도 중복거래 발생 안하는게 좋겠는데"). triggerBotReaction이 독립 호출로 분리되면서, 유저가 짧은 간격으로 두 번 거래하면 트리거도 두 번 겹쳐서 들어올 수 있게 됐다 — 그대로 두면 같은 봇이 패턴 두 개를 동시에 실행해 매매가 뒤섞이거나(봇 존재 확인 전에 두 요청이 겹치면 봇이 2개 생기는 스폰 경합까지 발생할 수 있었다). botLocks/{'{realUid}'}에 RTDB 트랜잭션으로 "현재 잠겨 있지 않을 때만 내가 잠근다"를 원자적으로 처리하는 락을 추가해, maybeSpawnAndRunBot 전체(스폰 판정 + 패턴 실행)를 이 락으로 감쌌다. 이미 진행 중인 패턴이 있으면 뒤이은 트리거는 대기열에 쌓지 않고 그냥 건너뛴다(사용자가 원한 건 "나중에 실행"이 아니라 "중복 자체가 안 생기는 것"). 인스턴스가 중간에 죽어 락 해제를 못 타는 극단적인 경우를 대비해 60초 지나면 자동으로 만료되는 안전장치도 뒀다(패턴 최장 시간 20~25초의 넉넉한 배수).

거래량 랭킹(TOP5) 갱신도 봇에 동일 적용(2026-08-27, 사용자 지시 — "봇 거래량 갱신도 똑같이 적용해줘"). 원래 rankings/top5 갱신 로직은 trade.js의 실제 거래 경로 안에만 있었는데, 실제 유저의 거래 직후 봇이 반응하는 순서상 봇이 만든 거래량 증가분은 그 트리거가 된 거래의 랭킹 계산엔 잡히지 않고 다음 실거래 때까지 지연되는 문제가 있었다. 로직을 common.js의 updateVolumeRanking(db, stockId, name, price, volume)으로 공용화해 trade.js·tradingBot.js 양쪽에서 재사용 — 봇 주문 1건이 체결될 때마다 실제 거래와 똑같이 갱신을 "시도"하고, 기존 RANKING_DEBOUNCE_MS(30초) 디바운스도 동일하게 적용돼 한 패턴에서 5~20건이 연달아 나가도 실제 쓰기 횟수는 자연스럽게 제한된다.

  • node -c로 전체 신규/수정 파일 구문 검사 통과, 가짜 RTDB로 격리 시뮬레이션해 조건1(30초 미만 시 미발동)·조건2(확률 발동)·1인당 1개 고정·자산/보유량 초과 시 주문 스킵·2인 이상 접속 시 서로 다른 봇 배정을 전부 확인.
  • 배포 직후 실제 사이트 접속 테스트 중 presence 쓰기가 permission_denied로 막히는 걸 발견 — database.rules.json이 lastSeen 외 필드를 전부 거부하는 화이트리스트 구조였다. connectedAt을 허용 필드로 추가하고 4개 자매 레포(StreamBet-Market, soop-stock-market, interior-3d-viewer, streamer-life-game)에 동일하게 동기화한 뒤 --dry-run 확인 후 배포해 해결.
  • 라이브 실거래 클릭 테스트는 실제 운영 중인 공유 데이터(시세·잭팟 등)를 건드리는 작업이라 자동 승인 분류기가 차단 — 격리 시뮬레이션과 코드 리뷰로 로직을 검증했고, 실제 화면에서의 최종 확인은 사용자가 직접 진행.
