1서비스 개요

SOOP STOCK 거래소는 SOOP(숲) 스트리머를 하나의 "종목"으로 삼아, 유저가 가상 자산으로 매수·매도하며 시세 변동을 즐기는 웹 기반 모의투자 서비스입니다. 실제 화폐가 오가지 않는 엔터테인먼트 목적의 팬 참여형 미니게임이며, Firebase Realtime Database를 백엔드로 사용해 모든 유저에게 실시간으로 시세·랭킹이 동기화됩니다.

  • 플랫폼: 단일 페이지 웹앱 (Vanilla JS + Firebase, 정적 호스팅 / GitHub Pages)
  • 대상: 스트리머 팬덤 커뮤니티, 익명 방문자 포함 누구나 즉시 참여 가능
  • 수익 모델: 배너 홍보(우측 랭킹 배너, 차트 하단 광고 배너), 최상단 고정 노출, 중계방 홍보 판매 + 라이브 방송 후원 기반 자산 충전(룰렛 이벤트 연계) + 플레이타임 초과분 게임머니 충전

2핵심 컨셉

📈 실시간 가상 시세

매수/매도 체결마다 가격에 즉시 영향(시장 충격)을 주는 방식으로, 실제 주식시장과 유사한 체감을 제공합니다.

🕯️ 분봉 캔들차트

체결 데이터를 1분 단위로 집계해 Chart.js 금융 차트로 시각화, 기간/분봉 단위를 유저가 선택할 수 있습니다.

🏆 실시간 랭킹 · 배너

거래량 상위 5개 종목을 주기적으로 집계해 노출하고, 스트리머 홍보 배너로 수익화합니다.

4주요 기능

4.1 종목 리스트 & 검색

  • 페이지 진입 시 전체 종목을 1회 조회(get)해 검색/정렬 기준 데이터(allStocks)를 구성
  • 가격순 정렬 후 상위 100개 또는 검색어와 일치하는 종목만 카드로 렌더링
  • 검색창 입력 시 종목명 기준 즉시 필터링 → 노출 목록이 바뀌면 구독 대상도 함께 갱신
  • 등락률에 따라 상승(빨강)하락(파랑) 색상 구분, 카드 내 스파크라인으로 최근 추세 시각화 — 가격 히스토리·등락률은 서버에 저장하지 않고, 클라이언트가 실시간 구독으로 받는 가격 틱을 로컬에 최대 20개까지 쌓아 직접 계산(데이터 사용량 절감)

4.1.1 실시간 구독 최적화 (노출 종목만 갱신)

  • 전체 종목을 항상 실시간 구독하던 방식에서, 현재 화면에 렌더링된 종목만 개별 구독하는 방식으로 전환
  • 검색/정렬 결과가 바뀌어 화면에서 사라진 종목은 구독을 즉시 해제하고, 새로 노출된 종목만 구독을 추가 (syncStockSubscriptions())
  • 보유 중인 종목은 목록에 노출되지 않아도 내 보유 주식 패널의 실시간 손익 반영을 위해 예외적으로 항상 구독 유지
  • 목적: 종목 수가 많아져도 불필요한 실시간 트래픽/DB 읽기 비용이 늘지 않도록 화면에 보이는 데이터만 최신 상태로 유지

4.2 캔들 차트

  • 체결 시마다 candlesticks/{stockId}/{분단위 timestamp}에 OHLCV 데이터 기록
  • 기간 탭(예: 10분/1시간 등)과 분봉 단위 탭을 조합해 조회 범위를 조정
  • 최대 360분 데이터만 보관, 이전 데이터는 주기적으로 삭제되어 DB 용량 관리
  • 차트 호버 시 캔들 정보(시가/고가/저가/종가/거래량) 툴팁 표시

4.3 랭킹 시스템

  • 매매 체결(trade Cloud Function) 마지막 단계에서 서버가 직접 TOP5를 갱신 — 클라이언트가 rankings/top5를 직접 쓰던 방식은 임의 조작이 가능한 구멍이라 서버로 이전됨
  • 거래량 지표는 델타 누적이 아니라 stocks/{id}.volume(누적 거래량) 절대값을 그대로 사용해 드리프트 없이 계산
  • 같은 종목이 너무 잦게 반영되지 않도록 마지막 저장 후 30초 이내면 이번 반영은 건너뜀(디바운스)
  • 집계된 TOP5는 rankings/top5에 저장되어 모든 유저에게 동일하게 노출 (클라이언트는 읽기 전용 구독만 수행)

4.4 홍보 배너 / 광고 — 셀프 신청 & 즉시 적용

과거엔 관리자가 신청마다 "진짜 상장된 스트리머가 맞는지"까지 검수해야 했으나, 현재는 닉네임이 이미 상장된 종목명인지만 신청 시점에 자동 확인하도록 바뀌어 관리자 승인 단계 자체가 사라졌다 — 상장 여부는 상장 신청 승인 시점에 이미 한 번 걸러지기 때문이다. 상장 안 된 이름이면 신청 폼이 "먼저 상장 신청을 해주세요"로 막고, 상장된 이름이면 게임자산 차감과 동시에 즉시 적용된다.

  • 우측 랭킹 배너: 이미 상장된 종목명 검색(자동완성) + 스트리머 아이디 입력 → 아이디 기반 프로필 이미지(stimg.sooplive.com/LOGO/...)를 자동으로 배너 이미지로 사용 → 노출 기간(최대 7일) 선택 → 신청 즉시 적용, 검수 없음
  • 차트 하단 배너 — 유일하게 부분 검수가 남아있는 기능: 슬롯/기간 예약과 배너 이미지 승인이 분리되어 있다. 종목 카드를 클릭해 차트 모달을 연 상태에서 신청하면(그 시점 종목ID가 고정), 신청 즉시 chartBanner/{stockId}에 기간이 예약되지만 배너 이미지(bannerImg)는 비워둔 채 관리자 승인을 받아야 실제로 노출된다 — 사용자가 임의 이미지 URL을 즉시 노출시킬 수 없도록 이미지 검수만은 남겨둔 것
  • 중복 신청 차단: 어떤 종목에 이미지 미승인 상태로 예약된 배너가 있으면(이미지 없이 기간만 예약된 상태), 그 종목에는 다른 유저가 새로 신청할 수 없다 — 차트 모달에도 "⏳ 배너 홍보 승인 검수중이에요"로 표시되고 신청 버튼이 비활성화된다
  • 홍보 페이지 링크 자동 생성: 두 배너 모두 신청자가 입력한 스트리머 아이디로 https://www.sooplive.com/station/{아이디} 링크를 서버가 자동 계산 — 링크를 직접 입력받지 않는다
  • 결제: 신청 시점에 서버(Cloud Function)가 신청자의 보유 게임자산(현금)에서 기간 × 단가를 바로 차감
  • 종목별 개별 노출(차트 배너): 전체 종목 공동 노출이 아닌 chartBanner/{stockId} 단위로 종목마다 독립적인 배너를 설정. 종목이 삭제되면 연결된 chartBanner도 함께 삭제되어 orphan 데이터가 남지 않는다
  • 기간 만료: 노출 기간이 지나면 메인페이지에서 자동으로 숨겨지며, 관리자 페이지의 "만료된 홍보" 탭에서 재연장하거나 완전히 삭제할 수 있음
  • 재신청(우측 배너): 이미 홍보 중(만료 전)인 종목으로 재신청하면, 오늘부터 새로 계산하지 않고 기존 만료일에 이어서 연장됨 — 차트 배너는 종목별 개별 신청이라 이런 특별 처리 없이 그대로 갱신
  • 관리자 페이지의 역할 변화: "신규 신청" 검수 큐는 우측 배너·최상단 고정·중계방에서는 사실상 예전 방식(레거시) 기록 확인용으로만 남아있고, 실제 운영은 "진행중/만료" 탭에서 내용 수정·조기 삭제 위주로 이뤄진다. 차트 배너만 "이미지 승인 대기" 큐가 실질적으로 계속 쓰인다
상품단가적용 방식
우측 랭킹 배너게임자산 100만원 / 1일 (최대 7일)신청 즉시 적용 (검수 없음)
차트 하단 배너 (종목별)게임자산 200만원 / 1일 (최대 7일)슬롯/기간은 즉시 예약, 이미지만 관리자 승인 후 노출

4.5 최상단 고정 노출 — 종목 리스트 최상단 슬롯 판매

종목 리스트는 원래 가격순 정렬이지만, 신청된 종목은 정렬과 무관하게 리스트 최상단에 최대 3개까지 고정 노출된다. 배너와 달리 이미 상장된 종목을 대상으로 하는 기능이라, 신청 폼도 닉네임/아이디 입력이 아니라 종목명 검색(자동완성)으로 대상을 고른다. 관리자 검수 없이 신청 즉시 적용된다.

  • 단가: 시간당 게임자산 50만원, 최소 1시간 ~ 최대 12시간 신청 가능
  • 슬롯: 동시 최대 3개 종목만 고정 가능 — 신청 시점에 슬롯 여유를 검사해, 가득 찬 경우 신청 자체가 거부됨(관리자가 기존 고정을 조기 해제하거나 만료를 기다려야 함)
  • 재신청(연장): 이미 고정 중인 종목이 재신청되면 우측 배너와 동일하게 남은 시간에 이어서 연장(슬롯을 새로 차지하는 게 아니므로 슬롯 검사 대상에서 제외)
  • 실시간 노출 보장: 고정된 종목이 가격순 top100 밖(원래는 화면에 안 보일 종목)이어도 항상 표시되도록, pinnedStocks/{stockId} 경량 마커 경로를 클라이언트가 상시 구독해 "항상 구독 유지" 대상에 포함시킨다
  • 카드에는 📌 배지와 금색 테두리로 일반 종목과 구분 표시, 검색 중일 때는 안내 카드가 숨겨짐

4.6 중계방 홍보 — 지금 플레이 중인 스트리머 소개

이미 상장된 종목명 검색(자동완성) + 아이디 입력 → 아이디 기반 미리보기 자동 표시 → 신청 즉시 게임자산 차감과 동시에 적용, 관리자 검수 없음. 재신청 시 "연장"하는 배너와 달리 이미 진행 중인 종목은 신청 자체를 거부한다(단순 중복 방지, 연장 로직 없음).

  • 단가: 시간당 게임자산 30만원, 최소 1시간 ~ 최대 8시간
  • 인원: 동시 최대 3명까지만 등록 가능 — 신청 시점에 인원 초과 여부 검사
  • 노출 위치: 종목 리스트 위 "🎥 중계방" 영역, 클릭 시 방송국으로 새 탭 이동
  • 카드 너비 자동 분배: 등록 인원(1~3명)에 따라 각 카드가 flex: 1 1 0으로 균등 분배돼 100%(1명) / 50%(2명) / 33%(3명) 너비로 자동 조정됨
  • 배너 목록과 동일하게 페이지 로드 시 1회만 조회(실시간 구독 없음)해 비용을 아낀다

4.9 종목 상장 신청 — 없는 종목 무료 신규 상장

검색해도 없는 스트리머를 유저가 직접 상장 요청할 수 있다. 무료지만(비용 차감 없음) 아무 이름이나 즉시 상장되면 도배성 종목이 난립할 수 있으므로, 다른 셀프 신청 기능과 달리 여전히 관리자 승인이 필요하다.

  • 제약: 종목명 최대 12자, 1분에 1회 신청 제한(매크로 방지 쿨다운), 이미 상장됐거나 동일 이름으로 대기 중인 신청이 있으면 거부
  • 승인: 관리자가 승인하면 그 순간 시작가 10,000원으로 새 종목이 상장됨(오타 발견 시 승인하며 이름 수정 가능)
  • 대상: 카카오 연동(또는 관리자) 유저만 신청 가능

4.10 종목 거래 동결 (서킷브레이커)

가격이 무작정 오르기만 하는 걸 막는 안전장치. 매수 체결마다 서버(trade)가 자동 판정하며, 별도 신청 없이 조건 충족 시 즉시 발동한다.

  • 발동 조건: 매수 거래가 실제로 있었던 최근 1분봉 5개의 종가가 전부 100만원 이상이면 그 5번째 매수 체결 순간 동결(평균이 아닌 "전부 다" 조건 — 단발성 펌프에 강함)
  • 동결 중: 매수·매도 모두 전면 차단
  • 해제 제약: 동결 직후 5분간(STOCK_FREEZE_COOLDOWN_MS)은 누구도 해제 불가, 동결을 유발한 계정 본인도 해제 불가 — 그 외 유저가 5분 경과 후 선착순 1명만 해제 가능
  • 해제 방법 2가지: ① 게임자산 100만원 지출 → 즉시 셀프서비스, 200만원 보상(순이익 100만원) + 주가 50만원으로 강제 인하 / ② 라이브 방송 후원(별풍선 50개) → 신청 후 관리자 검수, 100만원 보상
  • 미해제 시: 동결 후 12시간(STOCK_DELIST_DEADLINE_MS) 안에 해제되지 않으면 자동 상장폐지 — 보유 중이던 모든 유저의 주식이 전액 소멸(환급 없음). 상장폐지까지 남은 유예시간은 메인페이지 동결 배너에 카운트다운으로 표시되며, 마감 임박 시 별도 경고가 뜬다
  • 스케줄러: checkFrozenStockDelistings가 주기적으로 실행되어 유예시간이 지난 동결 종목을 자동으로 상장폐지 처리

4.11 내 손익 랭킹 — 순수 매매 손익 순위

보너스·후원 당첨금·홍보 신청 비용 등 매매 외 현금흐름은 전혀 반영하지 않는 순수 매매 손익만 집계하는 익명 리더보드.

  • 계산: 매도 체결마다 trade()가 평단가 기준으로 users/{uid}.realizedPL에 실현손익만 누적하고, 랭킹 확인 시점에 서버가 이 값을 그대로 반영한다 — 미실현(보유 중 종목의 평가손익)은 의도적으로 반영하지 않는다. 현재가는 본인이 소량 매수만으로도 순간적으로 밀어올릴 수 있는 값이라, 대량 보유 물량에 그대로 곱해 마킹하면 팔지 않고도 가짜 이익을 순위표에 영구히 박아둘 수 있는 구멍이 있었다(초기 설계의 결함, 발견 후 수정). 클라이언트가 보낸 숫자는 애초에 신뢰하지 않고 매번 서버가 원본 데이터로 재계산한다
  • "예상 순위 보기"(무료)와 "공식 게시"(유료) 분리: 순위가 궁금해서 캐주얼하게 열어보는 행위 자체에 비용을 매기면 재접속을 유도해야 할 기능이 오히려 재접속을 억제하는 역설이 생긴다. rankings/profitEntries가 인기 TOP5와 동일하게 이미 공개 읽기 경로라, 클라이언트가 이미 들고 있는 내 realizedPL과 조합해 서버 호출 없이 무료로 "지금 게시하면 몇 등일지" 계산해 보여준다(orderByChild('value').startAt(내손익+1)로 나보다 높은 공개 엔트리 수를 세는 방식). 실제로 순위표에 이름을 올려 다른 유저에게 보이게 하는 행위만 유료(checkProfitRanking, 50만원)로 남긴다 — 상시 폴링 억제와 서버 재계산 비용 절감 목적은 그대로 유지됨
  • 대상: 확인/게시 모두 카카오 또는 구글로 계정을 보호한 유저만 가능(어뷰징 방지)
  • 표시: 실제 닉네임 대신 트레이더-XXXXXX 형태의 익명 ID로만 노출, 상위 10명 + 내 순위를 함께 보여줌
  • 저장 구조: rankings/profitEntries/{uid}에 value로 인덱싱(.indexOn)된 경로에 기록해 RTDB 쿼리(orderByChild('value').limitToLast(N))만으로 상위 N명을 조회 — 별도 스케줄 집계 작업이 없다

4.12 출석 보상 — 1~7일차 순환형 출석부

연속 스트릭(하루라도 놓치면 0으로 리셋)이 아니라 "출석부" 방식 — 하루 놓쳐도 완전히 잃는 게 아니라 1일차로 되돌아가는 정도라 이탈 부담이 적다. 지갑 바의 "🎁 출석 보상 받기" 버튼을 눌러야 지급되는(자동 팝업 아닌) 방식이라 팝업 피로를 만들지 않는다.

일차1234567
보상3만원5만원7만원10만원13만원16만원30만원
  • 대상: 카카오 또는 구글로 계정을 보호한 유저만 — 익명 계정은 브라우저 데이터만 지우면 무한정 새로 만들 수 있어 대상에 넣으면 1일차 보상만 반복 파밍하는 어뷰징이 바로 생긴다
  • 판정: users/{uid}.lastAttendanceDate(KST 날짜)가 어제면 다음 일차로 순환(7일차 다음은 1일차), 그 외(이틀 이상 공백 또는 첫 출석)면 1일차로 리셋. RTDB 트랜잭션으로 판정과 갱신을 묶어 더블클릭 등으로 중복 지급되지 않게 함
  • 버튼 상태: 오늘 아직 안 받았으면 파란 테두리로 강조되고 다음 일차가 몇 일차인지 미리 보여줌("🎁 출석 보상 받기 (3일차)"), 오늘 이미 받았으면 비활성화("✅ 오늘 출석 완료")
  • 시간 보너스 없음: 하루 무료 이용시간(플레이타임)과는 완전히 별개로, 순수 게임자산만 지급한다

4.7 자산 충전 — 라이브 방송 후원 기반 게임자산 지급

실제 후원(별풍선 등)은 라이브 방송에서 별도로 이뤄지고, 이 기능은 "후원했다"는 신청만 접수한다. 신청 시점엔 차감/지급이 전혀 없고, 관리자가 방송에서 후원을 직접 확인한 뒤 지급액을 입력해 승인하는 방식이다.

  • 신청 흐름: ① "라이브 방송으로 이동" 버튼으로 방송 페이지 이동해 후원 → ② 다시 모달을 열어 닉네임·아이디로 신청서 작성 → ③ 관리자가 후원 내역과 대조 확인 후 지급
  • 거절 시 환불 없음: 신청 시 아무것도 차감되지 않았으므로 거절은 단순히 상태만 변경
  • 지급액 결정(운영 방식): 방송 중 진행되는 룰렛 이벤트(위플랩 브라우저 소스 — 이 코드베이스 밖에서 별도로 실행됨)의 결과에 따라 관리자가 지급액을 직접 입력한다. 예: 33개(3,300원) 후원 1회당 룰렛 1회, 95% 확률로 50만원 / 5% 확률로 500만원 당첨 — 이 규칙 자체는 서버 코드가 아니라 운영 정책이며, 관리자는 결과값을 approveCashChargeRequest에 그대로 입력만 하면 된다

4.8 플레이타임 제한 — 하루 무료 이용 시간 & 게임머니 셀프 충전

Firebase 실시간 구독(대역폭) 비용을 관리하기 위해 하루 무료 이용 시간을 두고, 초과분은 메인페이지에서 게임머니로 직접 충전할 수 있다.

계정 유형하루 무료 이용 시간
익명 유저15분
카카오 연동 유저60분
관리자무제한
  • 측정 방식: 클라이언트가 20초 간격으로 서버(heartbeat)를 호출하고, 경과 시간은 클라이언트 자기신고가 아니라 서버에 저장된 마지막 호출 시각과의 실제 시간차로 계산 — 절전/네트워크 단절 등 이상치는 90초로 상한을 둬 과다 차감을 방지
  • 소진 시 처리: 클라이언트가 스스로 모든 실시간 리스너를 해제 — RTDB 보안 규칙으로 읽기를 강제 차단하는 방식은 이미 붙어있는 리스너에 실시간 재적용이 안 되는 신뢰성 문제가 있어, 이 "자발적 구독 해제" 방식을 채택했다. trade() 함수도 동일한 quota를 서버에서 재검증해, 화면 구독을 우회해도 실제 거래는 막는다
  • 우회 방지(보안 수정): 과거엔 trade()가 heartbeat가 미리 쌓아둔 사용량을 "읽기"만 했는데, 이 경우 클라이언트가 heartbeat 호출을 아예 건너뛰고 trade 등을 직접 호출하면 사용량이 영원히 0으로 남아 하루 이용시간 제한이 무력화됐다. 지금은 trade() 등 활동성 함수가 heartbeat와 동일한 경과시간 트랜잭션(touchHeartbeat)을 직접 수행해, 별도 하트비트 호출 없이도 자체적으로 시계가 진행되도록 수정됨
  • 탭 전환 대응: 브라우저 탭이 백그라운드로 가면 하트비트·구독을 모두 멈추고, 다시 보이면 재개 — "실제로 보고 있는 시간"만 차감
  • 충전 단가(누진): 기준단가 = 총자산(현금+보유주식 평가금액) × 10% (1시간), 당일 n번째 추가 구매마다 할증 +10%p씩 누적, 최대 +50%에서 상한 — 자산이 많은 유저일수록 비례해 비싸지는 구조. 자정(KST) 기준으로 사용량·구매 횟수 모두 초기화
  • UI: 지갑 바에 상시 타이머(MM:SS / MM:SS) 표시, 5분 전 1회성 경고, 소진 시 "카카오 연동" / "시간 충전" 중 선택하는 닫기 불가 모달 노출
  • 테스트 기간 제한(TEST_PERIOD_ACTIVE): 현재 테스트 기간 중에는 관리자를 제외한 모든 유저의 시간 충전(유료) 기능만 서버에서 막혀 있다 — 하루 무료 이용시간(익명 15분/카카오 60분)은 테스트 기간과 무관하게 정상 제공됨. 테스트 종료 시 서버(common.js)와 클라이언트(index.html) 양쪽의 이 플래그를 false로 바꿔 배포해야 함
참고 — 로그인(계정 보호) 필수 기능 — 자산충전·우측/차트 배너·최상단 고정 노출·중계방 신청·종목 상장 신청·손익 랭킹 확인·출석 보상은 카카오 또는 구글로 계정을 보호한 유저(또는 관리자)만 신청할 수 있다. 이 앱의 익명 로그인은 접속 시 자동으로 이뤄지므로, 매크로·도배성 신청을 어렵게 하고 실제 신원이 있는 유저만 게임자산을 실제 홍보 슬롯으로 바꿀 수 있게 하기 위한 제한이다. 서버(requireLinkedUser)가 최종 방어선이고, 클라이언트는 모달을 열기 전에 미리 안내해 폼을 다 채운 뒤 막히지 않도록 돕는다.

5거래(매매) 로직

모든 매매는 클라이언트가 아닌 Cloud Function(trade callable, functions/trade.js)이 Admin SDK로 서버에서 계산·기록합니다. 클라이언트는 종목 id·매수/매도·수량만 전달하고, 가격 계산·잔고 검증·기록은 전부 서버 책임입니다. stocks/{id}·users/{uid}·candlesticks에 대한 클라이언트 직접 쓰기는 database.rules.json에서 전부 false로 막혀 있어, 관리자 페이지를 포함해 어떤 클라이언트도 이 경로들을 직접 조작할 수 없고 오직 Cloud Function(Admin SDK)만 기록합니다.

가격 결정 공식

  • 시장 충격(impact): 0.001 × 수량
  • 스프레드(spread): 0.0005
  • 매도 수수료(fee): 0.3%
  • 매수가 = 신규가 × (1 + spread), 매도가 = 신규가 × (1 − spread)

  • 매수 시 잔액 부족 검증, 매도 시 보유 수량 부족 검증
  • 체결 시 평단가(avg) 자동 재계산, 매수/매도 효과음 재생

Cloud Function 내부에서 ⓪ 사전 검증(쿨다운·매도 보유량 — 가격과 무관하게 확정 판정 가능한 것만) → ① 종목 가격 트랜잭션 → ② 유저 잔고/보유수량 트랜잭션(쿨다운·잔액·보유량 최종 검증) → ③ 분봉 캔들 기록 → ④ 거래량 랭킹 갱신 순으로 처리한 뒤, 결과(체결가·잔고·보유수량)를 클라이언트에 반환합니다. 0단계 사전 검증은 무거운 가격 트랜잭션을 타기 전에 명백히 잘못된 요청을 걸러내 비용을 줄이고, 그 이후 단계에서 실패가 나면(주로 드문 동시성 충돌) 종목 가격 변경을 상대적 보정으로 되돌려 보유하지 않은 종목의 시세가 조작되는 일을 막습니다. 랭킹 반영도 더 이상 클라이언트가 하지 않고 이 단계에서 서버가 직접 처리합니다.

6인증 · 관리자 모드

  • 일반 유저: 별도 로그인 없이 Firebase 익명 인증(signInAnonymously)으로 자동 참여, UID 기준으로 자산/보유 종목이 저장됨. 최초 접속 시 서버(initializeUser Cloud Function)가 초기 자산 50만원을 지급
  • 관리자 인증: Ctrl + Enter 입력 시 구글 로그인 팝업 실행 → 로그인 계정이 관리자 이메일과 일치하면 관리자 모드 활성화
  • 관리자 모드 활성화 시 점검 오버레이를 스킵하고 정상 서비스 화면으로 진입 (점검 중에도 관리자 본인은 접속/점검 확인 가능)
  • 관리자 계정은 별도 관리자 페이지(soop-stocks-admin-gate16103.html)와 동일 계정을 사용

계정 보호 — 카카오·구글 로그인 연동

익명 계정의 자산을 기기 변경·브라우저 데이터 삭제로부터 지키기 위한 기능. 카카오·구글 둘 중 아무거나(또는 둘 다) 연동할 수 있고, 지갑 바에는 미연동 시 "🔒 계정 보호하기" 통합 버튼 하나만 노출 → 클릭 시 카카오/구글 선택 모달이 뜬다. 두 방식 모두 닉네임·이름·프로필 사진 등 개인정보는 전혀 저장하지 않고 식별용 ID만 사용한다 — 실명 노출을 꺼리는 스트리머 등의 진입장벽을 낮추기 위함.

방식구현
카카오 (kakao.js)Firebase 기본 미지원 제공자라 우회 구현 — 클라이언트가 카카오 JS SDK로 access token을 받아 서버(linkKakaoAccount)에 전달, 서버가 카카오 API로 토큰을 검증해 고유 ID 확인 후 kakaoLinks/{kakaoId}에 uid를 직접 매핑
구글 (google.js)Firebase 기본 지원 제공자라 훨씬 단순 — 클라이언트가 linkWithPopup(auth.currentUser, googleProvider)로 지금 쓰던 익명 uid에 구글 자격증명을 그대로 이어붙임(별도 매핑 테이블 불필요). 서버(linkGoogleAccount)는 ID 토큰의 firebase.identities['google.com']으로 "정말 연동됐는지"만 재검증하고 보너스 지급·googleLinked 마킹을 한다
  • 최초 보호: 카카오·구글 중 처음 연동하는 쪽에서 보너스 50만원 지급 (초기 자산 50만원과 합쳐 100만원). 나중에 나머지 하나를 추가로 연동해도(이중 보호 목적으로 둘 다 걸어두는 것은 허용) 보너스는 중복 지급되지 않음 — 두 연동 함수 모두 상대편 플래그(kakaoLinked/googleLinked)가 이미 켜져 있으면 지급을 건너뜀
  • 다른 기기에서 로그인("합류") 흐름: 이미 다른 uid에 연동된 계정으로 로그인하면, 카카오는 서버가 발급한 커스텀 토큰으로(signInWithCustomToken), 구글은 Firebase가 던지는 auth/credential-already-in-use 에러의 credential로(signInWithCredential) 기존 계정으로 전환한다. 안내 문구는 "전환하시겠습니까(진행 상황이 사라집니다)"가 아니라 "이미 보호된 계정을 발견했어요! 이 기기에서도 이어서 플레이할까요?"로 합류·동기화 프레이밍을 사용 — 전환 이후엔 두 기기가 동시에 같은 계정을 실시간 구독하므로 사실상 계정 공유가 그대로 지원된다
  • 유도 시점(잔액 부족 순간 / 자산 100만원 첫 초과 순간): 두 시점 모두 특정 제공자를 바로 호출하지 않고 계정 보호 선택 모달을 연다 — 문제와 해결책이 같은 순간에 붙는 자연스러운 유도 타이밍은 유지하되, 어떤 방식을 쓸지는 유저가 그 자리에서 고른다
  • 2026-07 정책 변경(20만+80만 → 50만+50만) 소급 보정: 정책 변경 이전 생성된 익명 유저는 20만원만 받은 상태라, 실제로 거래해본(=진짜 이용한) 아직 미보호 유저에 한해 차액 30만원을 관리자 페이지에서 1회 보정 지급한다(previewAnonTopUp/applyAnonTopUp, users/{uid}/anonTopUpAppliedAt로 중복 지급 방지)
  • UI 상태 분기: 지갑 바에 둘 다 미연동 시에만 통합 유도 버튼, 하나라도 연동되면 버튼은 숨기고 연동 방식별 배지("✅ 카카오로 보호됨" / "✅ 구글로 보호됨" / 둘 다면 "✅ 카카오·구글로 보호됨")로 대체. 관리자(구글 로그인) 계정은 "✅ 구글 연동됨" 배지로 별도 표시
  • 로그아웃 기능은 의도적으로 만들지 않음 — 익명 유저가 실수로 로그아웃하면 사실상 계정을 잃는 것과 같아, 버튼 자체를 아예 노출하지 않는 쪽을 택함
  • kakaoLinks/{kakaoId} 경로는 클라이언트 직접 read/write를 전부 차단하고 서버(Admin SDK)에서만 다룸. 구글은 Firebase 자체가 uid↔자격증명 매핑을 관리해 별도 매핑 경로가 없음

관리자 페이지 기능 — 전부 Cloud Function 경유 (adminAction callable)

종목 시세 조정, 배너 검수/관리, 비활성 유저 정리 등 관리자 페이지의 모든 쓰기·민감 읽기 작업은 클라이언트가 {action, payload}만 전달하고, 실제 처리는 functions/admin.js의 adminAction 콜러블이 Admin SDK로 수행합니다. 함수 진입 시 auth.token.email === 관리자 이메일을 서버에서 재검증합니다.

7점검(유지보수) 모드

성격이 다른 점검 기능 2가지가 공존한다 — 하드 차단(LONG_MAINTENANCE)은 장기 점검용으로 페이지 진입 자체를 막고, 소프트 점검모드(maintenance/)는 관리자가 실시간으로 켜고 끄며 페이지는 그대로 보여준 채 활동(거래·홍보 신청 등)만 막는다.

점검 오버레이 노출 (전면 차단)
  • 점검 플래그(LONG_MAINTENANCE)는 index.html의 코드 상수로 on/off — 장기 점검 시 true로 설정, 배포 필요
  • 점검 중에는 일반 유저의 실시간 데이터 구독·거래 로직 자체가 실행되지 않아 서버 부하 및 오작동을 원천 차단
  • 점검 안내창에는 사유 안내와 개발자 방송국 바로가기 버튼 제공

7.2 소프트 점검모드 — 관리자 실시간 on/off, 활동만 차단

관리자 페이지의 "🛠️ 점검모드 관리" 패널에서 setMaintenanceMode 액션으로 즉시 켜고 끌 수 있다. LONG_MAINTENANCE와 달리 배포가 필요 없고, 페이지 자체는 정상적으로 보인다.

관리자: 점검모드 켜기
→
서버: maintenance/{active:true, startAt:+30초}
→
전 유저: "30초 후 점검 시작" 카운트다운 배너
→
30초 경과: "점검 진행 중" 배너로 전환 + 활동 차단
  • 표시 위치: 상시 노출되는 지갑 카드 내부 하단(#maintenance-banner) — 카운트다운 중엔 노란색, 활성화 후엔 빨간색으로 전환
  • 차단 범위: 거래(trade)와 배너/고정노출/중계방/자산충전/상장신청/동결해제/손익랭킹 확인 등 활동성 액션만 막힌다 — 시세 조회·차트 등 읽기 기능은 정상 작동
  • 관리자 예외: 관리자 계정은 점검모드가 켜져 있어도 활동이 그대로 가능(배너만 다른 유저와 동일하게 보임 — 점검 상태를 직접 확인할 수 있도록)
  • 서버 강제(보안 수정): 과거엔 blockIfMaintenance()가 클라이언트에서만 활동을 막아, 개발자도구 등으로 Cloud Function을 직접 호출하면 점검 중에도 매매·신청이 그대로 처리되는 우회 구멍이 있었다. 지금은 common.js의 requireNotInMaintenance 헬퍼가 trade·buyPlayTime을 포함한 활동성 함수 11곳 전부에서 서버 측으로도 동일하게 강제한다(관리자는 동일하게 예외)
  • 데이터 경로: maintenance — {active, startAt}, 공개 읽기(.read:true) / 클라이언트 직접 쓰기 차단(관리자 페이지도 adminAction 경유)
